# Millions of evolved neural nets on RX 7900 XT

Researched 2026-10-31. Research only; no GPU benchmarks or cloud instances run. Links are evidence, not instructions. “Calculated” and “recommendation” below distinguish analysis from measured results. GB means decimal; memory figures exclude simulation state unless stated.

## Verdict and throughput

**Recommendation: keep Rust + native wgpu/WGSL for 100–10,000-parameter independent brains integrated into the GPU simulation. CUDA is not required.** Native wgpu has Vulkan support, and compute need not create a window/surface. The relevant API is a dispatch over many agents, not one dispatch per brain. This recommendation follows the memory arithmetic below and [wgpu’s adapter/compute API](https://wgpu.rs/doc/wgpu/struct.Instance.html).

- With one observation vector per agent, the operation is **batched GEMV**: `y[a,o] = activation(sum_i W[a,o,i]*x[a,i]+b[a,o])`. Different matrices are legal storage-buffer data; WGSL’s built-in matrix types are small fixed shapes, but loops over arrays implement arbitrary dimensions. A batch dimension does not turn different weights into a large shared-weight GEMM. [WGSL types and statements](https://www.w3.org/TR/WGSL/)
- RX 7900 XT: **20 GB GDDR6, up to 800 GB/s external bandwidth, 51.5 TFLOP/s FP32**. AMD’s “effective bandwidth” cache metric is not a streaming-VRAM budget; use 800 GB/s for these weight streams. [AMD specifications](https://www.amd.com/en/products/graphics/desktops/radeon/7000-series/amd-radeon-rx-7900xt.html)
- **Calculated roofline**, weights read once per inference, one multiply-add counted as two operations: FP32 gives 0.5 FLOP/byte and at most 0.4 TFLOP/s from 800 GB/s; FP16 gives 1 FLOP/byte and 0.8 TFLOP/s. Neither approaches the FP32 compute peak. Caches, reuse and fusion can change traffic; instructions, activations and state add costs. This is a ceiling model, not a benchmark. [Hardware inputs](https://www.amd.com/en/products/graphics/desktops/radeon/7000-series/amd-radeon-rx-7900xt.html)
- For **1M agents × 1,000 weights**, FP32 streams 4 GB/step: ideal lower bound **5 ms**, hence at most **200 steps/s** for weight reads alone. At 100 weights: 0.4 GB, 0.5 ms, 2,000 steps/s; at 10,000: 40 GB, 50 ms, 20 steps/s, but that population does not fit. FP16 halves these bytes; INT8 quarters them. All are calculated from [800 GB/s](https://www.amd.com/en/products/graphics/desktops/radeon/7000-series/amd-radeon-rx-7900xt.html), excluding every other simulation cost.
- Suggested kernel experiments: one invocation per very tiny brain; one subgroup or workgroup per larger brain; adjacent lanes load adjacent weights; fuse activation/layers where register/shared-memory budgets allow. Benchmark agent-major versus weight-major layouts for the chosen lane mapping. Keep sensors, recurrent state, inference, mutation and actions on GPU; read back summaries. These are engineering hypotheses guided by [WGSL execution/memory rules](https://www.w3.org/TR/WGSL/#execution).
- Several rollout vectors per **same** genome, shared species brains, or multiple independent environments per policy can yield real GEMM reuse. More parameters alone do not solve GEMV’s low arithmetic intensity. [cuBLAS batched GEMM interface](https://docs.nvidia.com/cuda/cublas/index.html#cublas-t-gemmstridedbatched)

## Actual WGSL/wgpu limits, and alternatives

- **f16 is optional, not universally absent**: query/request `SHADER_F16`, then `enable f16;`. Without it, packed half weights can still be decoded with `unpack2x16float` into FP32. Explicit f16 storage plus f32 accumulation is possible by conversion; “no mixed precision” is false at the language level, but this does not promise a fused tensor-core mixed-precision instruction. [WGSL f16 and conversion rules](https://www.w3.org/TR/WGSL/#floating-point-types), [wgpu features](https://wgpu.rs/doc/wgpu/struct.Features.html)
- **Pointers exist** in WGSL (`ptr`, address-of, dereference), with address-space and usage restrictions. There is no general CUDA-style raw address arithmetic, heap allocation or arbitrary pointer graph. Represent variable topology with indices/offsets in buffers. [WGSL pointers](https://www.w3.org/TR/WGSL/#pointer-types)
- Portable WGSL has 32-bit integer scalars, not standard int64. **Native wgpu additionally exposes `SHADER_INT64`**, subject to backend support; it is not portable browser WebGPU. Query the actual adapter and use u32 offsets for the portable path. [Native feature definition](https://wgpu.rs/doc/wgpu/struct.FeaturesWGPU.html#associatedconstant.SHADER_INT64)
- **“4 GB bindings” is not a universal guaranteed allowance or a 4 GB total-VRAM ceiling.** wgpu 30 documents default storage binding **128 MiB**, default buffer **256 MiB**, with adapter-dependent raised limits; current fields are u64. Older versions and Vulkan `maxStorageBufferRange` may constrain a binding near/below 4 GiB. Query `adapter.limits()`, request supported limits, and shard populations into buffers/dispatches; u32 indexing also constrains shader addressability. [wgpu limits](https://wgpu.rs/doc/wgpu/struct.Limits.html), [Vulkan limits](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceLimits.html)
- **Subgroups** provide lane collectives/reductions under an optional feature; do not hard-code CUDA’s 32-lane warp. Native feature/backend availability and browser availability differ. [wgpu SUBGROUP](https://wgpu.rs/doc/wgpu/struct.FeaturesWGPU.html#associatedconstant.SUBGROUP), [WGSL subgroup built-ins](https://www.w3.org/TR/WGSL/#subgroup-builtin-functions)
- **Cooperative matrices** expose collective tile multiply-accumulate, with supported dimensions, operand/accumulator types and scope queried per driver. `VK_KHR_cooperative_matrix` is not implied by having f16 or “AI accelerators.” Query `vkGetPhysicalDeviceCooperativeMatrixPropertiesKHR`; do not promise RX 7900 XT matrix acceleration without its actual driver report. [Khronos extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_cooperative_matrix.html)
- Crucial current detail: **wgpu 30 has `EXPERIMENTAL_COOPERATIVE_MATRIX`, native only, currently 8×8 f32**. Its docs warn most AMD/NVIDIA Vulkan implementations expose f16 at larger sizes, making support limited. Thus “wgpu exposes no cooperative matrices” is outdated, but this feature is not a dependable tensor-core path here. `SHADER_F16` alone does not fix that mismatch. [Exact wgpu limitation](https://wgpu.rs/doc/wgpu/struct.FeaturesWGPU.html#associatedconstant.EXPERIMENTAL_COOPERATIVE_MATRIX)

| Stack | What it adds; consequence for this workload |
|---|---|
| Direct Vulkan (Rust `ash`, SPIR-V) | Broader extension control, buffer device addresses and driver-supported cooperative matrix shapes/types; more memory/synchronization work. Useful if a measured wgpu limitation blocks optimization, not an automatic GEMV speedup. [Vulkan guide](https://docs.vulkan.org/guide/latest/extensions/shader_features.html) |
| CUDA on NVIDIA | cuBLAS batched/strided GEMM, tensor-core mixed precision, mature libraries/profiling and multi-GPU ecosystem. Cannot execute CUDA directly on this Radeon. Most valuable when there is substantial reuse or a library already solves the workload. [cuBLAS](https://docs.nvidia.com/cuda/cublas/index.html) |
| HIP/ROCm on AMD | C++ compute kernels and rocBLAS batched/strided GEMM with extended datatypes; native compute/library route without replacing the Radeon. [rocBLAS API](https://rocm.docs.amd.com/projects/rocBLAS/en/latest/reference/level-3.html) |
| SYCL | C++ heterogeneous programming; Codeplay supplies AMD and NVIDIA backend plugins. Adds another compiler/runtime dependency, not immunity from bandwidth limits. [Codeplay plugins](https://codeplay.com/solutions/oneapi/plugins/) |
| Slang | Shader authoring targeting SPIR-V/CUDA; cooperative-vector operations can accelerate small neural inference on supporting NVIDIA hardware. Capability-specific, not a portable AMD guarantee. [Slang cooperative vectors](https://shader-slang.org/blog/2025/01/30/coop-vec-available/) |
| rust-gpu | Rust shader code compiled to SPIR-V, with a restricted GPU environment. Improves language sharing; does not itself supply BLAS or remove Vulkan hardware limits. [Platform support](https://rust-gpu.github.io/rust-gpu/book/platform-support.html) |

**ROCm on RX 7900 XT Linux: yes, officially listed**, including ROCm 7.2.1’s Radeon matrix; that matrix lists Ubuntu 24.04.4/22.04.5 and RHEL 10.1 and production PyTorch 2.9.1. That is evidence of a supported configuration, not validation of NixOS or every newer combination. The page says newer Core SDK documentation is unified from 7.13.0: select matching release/framework/OS rather than blindly installing “latest.” [AMD matrix](https://rocm.docs.amd.com/projects/radeon-ryzen/en/latest/docs/compatibility/compatibilityrad/native_linux/native_linux_compatibility.html)

## Evolved-only representations: capacity before compute

Calculated storage for **1M agents**, excluding padding, scales, biases and activations. FP/packed encodings derive from [WGSL scalar and packing facilities](https://www.w3.org/TR/WGSL/#pack-builtin-functions); they are capacity arithmetic, not accuracy/speed claims.

| Parameters/agent | FP32 | FP16 | INT8 packed | INT4 packed |
|---:|---:|---:|---:|---:|
| 100 | 0.4 GB | 0.2 GB | 0.1 GB | 0.05 GB |
| 1,000 | 4 GB | 2 GB | 1 GB | 0.5 GB |
| 10,000 | 40 GB | 20 GB | 10 GB | 5 GB |

- With a chosen **16 GB weight budget** out of 20 GB, 10k-param brains fit **400k FP32 / 800k FP16 / 1.6M INT8 / 3.2M INT4 agents**, before representation overhead. Keeping a complete second population halves those counts. Calculation: budget/(parameters × bytes); [capacity input](https://www.amd.com/en/products/graphics/desktops/radeon/7000-series/amd-radeon-rx-7900xt.html).
- **8/4 bit:** pack 4/8 weights per u32, extract/sign-extend and multiply by per-layer/block scales in FP32. Integer storage does not require integer activations. One FP32 scale per 64 weights adds **0.0625 byte/weight**, giving **1.0625 GB / 0.5625 GB** for 1B INT8/INT4 weights. Ideal weight-only bandwidth benefits versus FP32 become **3.76× / 7.11×**, not guaranteed runtime gains. Unpacking and scaling cost ALU work; use aligned blocks. [WGSL bit operations/packing](https://www.w3.org/TR/WGSL/#bit-expr)
- Evolution can evaluate the exact quantized phenotype; no backpropagation needs to survive quantization. Nevertheless 4-bit steps may erase useful mutations: evolve integer steps/scales, or retain compact higher-precision genotypes. Keeping a full FP32 master plus INT8 phenotype costs **5 bytes/weight**, worse capacity than FP32 alone. This is a proposed design and arithmetic, not an empirical quality result. [Example evolutionary policy pipeline](https://github.com/google/evojax)
- **Species base + sparse deltas, example:** 1,000 species × 10,000 FP16 weights = **20 MB** bases. Each of 1M agents stores species ID (4 B) plus 100 changed connections at (u16 index + f16 delta) = **404 MB** total agents; grand total **424 MB**, versus **20 GB** independent FP16 brains. No padding included. Group by species for base-cache reuse; scattered delta lookups add overhead and dense deltas lose most savings. This changes evolutionary expressiveness; it is a proposed indexed-buffer design using [WGSL storage](https://www.w3.org/TR/WGSL/#address-spaces).
- **Low-rank deltas, example:** a 100×100 matrix has 10k weights; rank-4 `U Vᵀ` needs **800 values**, 1.6 KB FP16/agent, versus 20 KB dense. Compute shared base `W₀x` plus `U(Vᵀx)`; about 800 extra MACs per agent, with reusable base weights. Approximation limits independent variation; proposal based on matrix factorization, not a measured evolved-net result. [Low-rank adaptation formulation](https://arxiv.org/abs/2106.09685)
- **Indirect encoding:** HyperNEAT/CPPN generates weights from neuron coordinates. Example 100-value FP32 genome = **400 MB** for 1M agents versus 40 GB for 10k explicit weights. Materializing weights restores the 40 GB problem; regenerating weights every step adds generator computation. Generate at birth/cache species where useful, and accept a bias toward structured connectivity. [Primary HyperNEAT research](https://jmlr.org/papers/volume11/verbancsics10a/verbancsics10a.pdf)
- **Sparse graphs:** 10% of 10k possible edges means 1,000 edges. At FP16 weight + u16 index, **4 KB/agent / 4 GB per million**, versus 20 KB/agent dense FP16, plus row offsets. With u32 indices it is 6 KB/agent; same-byte break-even density is below **50% / 33.3%** respectively, before offsets/padding. Irregular gathers/divergence can defeat speed gains; bucket topology/degree or use blocks. [Sparse storage principles](https://docs.nvidia.com/cuda/cusparse/storage_format.html)

## What existing frameworks actually do

| Framework | Relevant implementation and AMD portability |
|---|---|
| JAX | `vmap` maps a policy over a population axis, `jit` compiles/fuses the computation; no `grad` is required. Distinct weights must also have a mapped axis. AMD Linux uses AMD’s ROCm plugin with matching release versions; verify the card-specific build, not merely “JAX supports GPUs.” [Vectorization](https://docs.jax.dev/en/latest/automatic-vectorization.html), [installation](https://docs.jax.dev/en/latest/installation.html#amd-gpu-linux) |
| EvoJAX | Policies/tasks/evolution are JAX arrays and compiled operations; MLP source uses `jax.vmap(model.apply)` with population parameters. Conceptually portable through JAX ROCm, but legacy dependency compatibility and the whole task must be tested. This is parallel policy evaluation, not millions of Python model objects. [MLP source](https://github.com/google/evojax/blob/main/evojax/policy/mlp.py), [repository](https://github.com/google/evojax) |
| EvoX | Current main is **PyTorch-based**, with tensorized population algorithms and distributed workflows; previous JAX version lives on v0.9.0. AMD plausibility follows PyTorch ROCm, not a blanket EvoX hardware certification. [Current README](https://github.com/EMI-Group/evox) |
| Brax | JAX accelerator-oriented rigid-body environments and RL tooling; useful model for batched environments, not a ready particle-life simulation or evolutionary encoding. AMD path follows JAX and environment dependencies. Current README directs physics users toward MuJoCo/MJX. [Brax](https://github.com/google/brax) |
| PyTorch | Stack model state, use `torch.func.functional_call` + `vmap`; `bmm` handles differing matrices, inference mode avoids autograd storage. ROCm builds retain much of the `torch.cuda` API. For millions of tiny nets, avoid Python iteration and benchmark compiled/fused versus library kernels. [Ensemble tutorial](https://docs.pytorch.org/tutorials/intermediate/ensembling.html), [HIP semantics](https://docs.pytorch.org/docs/stable/notes/hip.html) |

Recommendation: borrow population axes, fused rollout loops and bucketed shapes from these frameworks. A Rust/wgpu simulation does not automatically share buffers with JAX/PyTorch; CPU transfers every step can erase benefits. Prototype scientific evolution separately in JAX/EvoX if their algorithms save development time; integrate only after measuring full-loop costs. [wgpu buffer mapping model](https://wgpu.rs/doc/wgpu/struct.Buffer.html)

## Headless clouds, multiple GPUs, and migration trigger

- **Headless native wgpu/Vulkan is possible in principle on supported NVIDIA devices**: select Vulkan and an adapter with no compatible surface; no desktop or browser required. Need Vulkan loader + matching NVIDIA ICD/userspace libraries, GPU device access and compute support. A CUDA-working container alone does not prove Vulkan works. [wgpu adapter API](https://wgpu.rs/doc/wgpu/struct.Instance.html#method.request_adapter), [NVIDIA Vulkan support](https://developer.nvidia.com/vulkan-driver)
- NVIDIA Container Toolkit distinguishes `compute` from **`graphics` capabilities required for Vulkan**. RunPod custom containers and Lambda GPU instances provide practical setup options; Vast requires suitable host/container configuration. Validate `vulkaninfo --summary` and a real compute dispatch on the rented hardware; check the selected GPU rather than assuming every NVIDIA datacenter SKU exposes Vulkan. [NVIDIA capabilities](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html#driver-capabilities), [RunPod templates](https://docs.runpod.io/pods/templates/overview), [Lambda instances](https://lambda.ai/instances)
- **Modal: conditional/unverified here.** Docs guarantee installed NVIDIA driver/CUDA execution and custom images, but the inspected documentation does not guarantee graphics-capability injection or Vulkan ICD availability. An environment variable inside a running container cannot by itself inject missing host libraries. Spend a minimal smoke-test allocation first; if no hardware Vulkan adapter appears, use CUDA there or a configurable GPU VM/Pod. [Modal driver contract](https://modal.com/docs/guide/cuda), [image customization](https://modal.com/docs/guide/images)
- **wgpu multi-GPU:** enumerate native adapters and create separate devices/queues; application shards agents or independent worlds. Ordinary buffers belong to a device; no portable automatic pooled VRAM, peer-to-peer copies or NCCL-style collectives. Host staging or backend-specific interop is needed for exchange. Spatial partitioning needs cross-GPU boundary traffic; independent worlds are easier. [Adapter enumeration](https://wgpu.rs/doc/wgpu/struct.Instance.html#method.enumerate_adapters), [device ownership](https://wgpu.rs/doc/wgpu/struct.Device.html)
- Modal supports multi-GPU requests (up to 8 for several types; A10 up to 4), multiplying GPU spend; that does not make wgpu distribute automatically. Prefer independent simulation replicas before splitting an interacting world. [Modal GPU guide](https://modal.com/docs/guide/gpu)
- **Small nets:** implement FP32 first, then FP16/packed INT8; keep simulation integrated, profile GPU timestamps and memory footprint. **Larger nets with reuse:** benchmark rocBLAS/HIP or PyTorch ROCm locally; direct Vulkan is an option when matrix extensions matter. **Large independent GEMV populations:** compression, VRAM and memory bandwidth still dominate; CUDA alone does not change the arithmetic. [rocBLAS](https://rocm.docs.amd.com/projects/rocBLAS/en/latest/reference/level-3.html), [cuBLAS](https://docs.nvidia.com/cuda/cublas/index.html)
- **When cloud/CUDA pays:** population exceeds practical 20 GB capacity, independent replicas need parallel throughput, or shared-weight/multi-rollout matrices can exploit optimized tensor-core libraries. Use the credits for matched full-simulation benchmarks on a modest GPU and a high-bandwidth large-memory GPU, then compare **agent-steps/$**, including setup/transfers. Do not predict millions-of-agent runtime from LLM tokens/s or peak tensor FLOPS. This is the recommendation derived from the capacity/roofline calculations and [current GPU costs](https://modal.com/pricing).
