# WebGPU/wgpu versus Vulkan for cellular automata

Research date: 2026-10-31. Research only; no local GPU benchmark or browser capability probe was run. Numbers below are published results, defaults, or source-derived limits, explicitly distinguished.

## Assessment

**Neither “20%” nor “10×” is a defensible universal penalty.** Browser compute can approach Vulkan for substantial GPU-resident kernels; dispatch-heavy applications can lose much more. No credible matched RX 7900 XT/RADV cellular-automata comparison was located. The closest stencil-like published comparison is marching cubes; the LLM evidence illustrates submission/synchronization sensitivity rather than a shader-throughput ceiling. [Marching cubes](https://www.willusher.io/graphics/2024/04/22/webgpu-marching-cubes/), [dispatch study](https://arxiv.org/html/2604.02344v1).

For this engine, first measure GPU time separately from CPU encoding, submission and readback. Keep states resident, batch generations, and render directly from GPU state. This is an engineering recommendation inferred from the distinction between sequential and synchronized measurements in the [dispatch study, §7.2](https://arxiv.org/html/2604.02344v1#S7.SS2).

## 2. Where overhead comes from

- **Shader checks:** Naga `BoundsCheckPolicy` has `Restrict`, `ReadZeroSkipWrite`, `Unchecked`; Naga's standalone default is unchecked, while consumers choose safety policies. Hardware robustness can replace injected checks. Repeated dynamic neighbor indexing may therefore add clamps, branches or predicates, but no fixed percentage follows. [Naga policy](https://docs.rs/naga/30.0.1/naga/proc/index/enum.BoundsCheckPolicy.html).
- **Native escape hatch:** unsafe `Device::create_shader_module_trusted(desc, ShaderRuntimeChecks { … })` controls bounds checks, loop bounding and other checks. `bounds_checks=false` avoids wgpu-injected checks but does not disable platform-provided checks. Caller must meet the documented safety conditions. [Checks](https://docs.rs/wgpu/30.0.1/wgpu/struct.ShaderRuntimeChecks.html).
- **Browser restriction:** trusted module creation simply calls ordinary `create_shader_module` on WebGPU; it cannot turn browser safety off. `create_shader_module_unchecked` has been deprecated since 24 in favor of the trusted API. [Device](https://docs.rs/wgpu/30.0.1/wgpu/struct.Device.html#method.create_shader_module_trusted).
- **CPU validation and barriers:** binding/pipeline/resource-usage validation and automatic synchronization are implementation work. Dependent CA generations also need memory ordering in raw Vulkan; that portion is not wholly removable overhead. No isolated, credible universal “validation nanoseconds per dispatch” measurement was found. Inspect the [wgpu compute command implementation](https://github.com/gfx-rs/wgpu/blob/v30.0.1/wgpu-core/src/command/compute.rs) and [Vulkan synchronization requirements](https://registry.khronos.org/vulkan/specs/latest/html/vkspec.html#synchronization).
- **Submission and browser IPC:** browser commands cross the browser's GPU-service boundary; WASM also uses JS bindings. Amortize this by encoding multiple dispatches per submission. Avoid CPU waits between generations; the dispatch study's single-operation tests include synchronization and substantially exceed its sequential results. [Dawn architecture](https://dawn.googlesource.com/dawn/+/refs/heads/main/docs/dawn/overview.md), [study methodology](https://arxiv.org/html/2604.02344v1#S7.SS2).
- **Mapping/readback:** a mapped buffer cannot simultaneously be used by GPU commands. Browser-portable readback uses a COPY_DST | MAP_READ staging buffer, asynchronous mapping, then unmapping; discrete-GPU transfers and synchronization can dominate small kernels. [wgpu Buffer documentation](https://docs.rs/wgpu/30.0.1/wgpu/struct.Buffer.html).
- **Compiler quality:** native wgpu translates WGSL through Naga to SPIR-V; Chromium/Dawn uses Tint. Both still feed the platform driver compiler. Different lowering, robustness transforms and optimization opportunities can change register pressure and instruction count; no credible universal Tint-versus-Naga throughput ratio was located. Inspect generated SPIR-V and final ISA for the actual CA kernel. [Naga](https://github.com/gfx-rs/wgpu/tree/v30.0.1/naga), [Tint](https://dawn.googlesource.com/dawn/+/refs/heads/main/src/tint/).
- **Workgroup zeroing:** WebGPU requires initialized workgroup memory; this may add stores and synchronization. Native `PipelineCompilationOptions::zero_initialize_workgroup_memory` can avoid that initialization when the shader initializes everything it reads; browser semantics remain mandatory. Benchmark tiled kernels with and without native zeroing. [API](https://docs.rs/wgpu/30.0.1/wgpu/struct.PipelineCompilationOptions.html).

## 3. Current version, limits and features

Latest documented published crate is **wgpu 30.0.1**, released August 22, 2026; cross-check against [crates.io](https://crates.io/crates/wgpu), [versioned docs](https://docs.rs/wgpu/30.0.1/wgpu/), [release history](https://github.com/gfx-rs/wgpu/releases/tag/v30.0.1). The crates.io JSON endpoint could not be retrieved in this environment, so the release/docs agreement is the version evidence.

Limits are capabilities to query and request, not promises based on VRAM capacity. `Limits::default()` remains conservative; device creation must explicitly request higher supported limits. [Limits API](https://docs.rs/wgpu/30.0.1/wgpu/struct.Limits.html).

| Limit | Portable wgpu default / WebGPU core baseline | Native/browser distinction |
|---|---|---|
| Storage binding bytes | 128 MiB | wgpu 30 field is **u64**, not u32; actual backend cap still applies. |
| Buffer allocation bytes | 256 MiB | `max_buffer_size: u64`; separate from binding size and available memory. |
| Storage buffers per stage | 8 | Native may request more; Chrome/Dawn internal ceiling currently 16. |
| Invocations per workgroup | 256 | Product x*y*z must fit this limit, not merely each axis. |
| Workgroup dimensions | 256 × 256 × 64 individual maxima | Query native and browser adapters; do not assume 1024 invocations is portable. |
| Workgroup memory | 16 KiB | Query higher limits before choosing shared-memory tiling. |
| Dispatch dimensions | 65,535 per axis | Tile large grids and pass a base offset. |

Table sources: [wgpu 30 Limits](https://docs.rs/wgpu/30.0.1/wgpu/struct.Limits.html), [WebGPU limits](https://gpuweb.github.io/gpuweb/#limits), [Dawn constants](https://github.com/google/dawn/blob/main/src/dawn/common/Constants.h).

**Critical RX 7900 XT/Linux restriction:** tagged wgpu 30.0.1 Vulkan code caps `max_buffer_size` at **2,147,483,647 bytes on Linux non-NVIDIA GPUs**, and storage bindings at `min(Vulkan maxStorageBufferRange, MAX_I32_BINDING_SIZE)`. Thus the u64 API does not grant a 20 GB single buffer on this target. Query exact exposed values and use multiple chunks. [Vulkan adapter source](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/vulkan/adapter.rs).

RADV Mesa 25.0 source reports `maxStorageBufferRange = UINT32_MAX` (**4,294,967,295**, not 4 GiB exactly). This is versioned source evidence, not a measurement of the installed driver. Chrome further tiers limits: Dawn source includes storage-binding tiers up to **4 GiB−4**, including **2 GiB−4**, and clamps binding size to buffer size/alignment. Exact RX 7900/Chrome values remain unmeasured; record `adapter.limits` and `device.limits` rather than claiming one universal Chrome value. [RADV](https://raw.githubusercontent.com/chaotic-cx/mesa-mirror/mesa-25.0.0/src/amd/vulkan/radv_physical_device.c), [Dawn tiers](https://github.com/google/dawn/blob/main/src/dawn/native/Limits.cpp).

Separately, wgpu indirect-call validation caps buffer sizes to u32 range while enabled. Disabling it does **not** remove the smaller Vulkan/Linux caps above. [Core source](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-core/src/instance.rs).

- **Push constants/immediates:** v28 replaced push-constant terminology/API with `IMMEDIATES`, `max_immediate_size`, `set_immediates`, and WGSL `var<immediate>`. Default size is zero; Vulkan typically supports 128–256 bytes. Browser support remains a proposal in wgpu 30 documentation, so use uniforms for the portable path. [Releases](https://github.com/gfx-rs/wgpu/releases), [feature](https://docs.rs/wgpu/30.0.1/wgpu/struct.FeaturesWebGPU.html#associatedconstant.IMMEDIATES).
- **64-bit integers:** `SHADER_INT64` enables i64/u64 on supporting native Vulkan/DX12/Metal; it is native-only, not portable WGSL/browser functionality. Detect it; browser code needs alternative representations. [Feature](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html#associatedconstant.SHADER_INT64).
- **Subgroups:** Chrome shipped optional `"subgroups"` in 134; request it and WGSL `enable subgroups`, with no fixed subgroup-width assumption. However, wgpu 30 still lists `SUBGROUP` among its native features: browser WebGPU support and this Rust wrapper's exposure must be checked separately. Do not promise browser subgroup support through this wgpu release solely because Chrome has it. [Chrome announcement](https://developer.chrome.com/blog/new-in-webgpu-134), [wgpu feature](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html#associatedconstant.SUBGROUP).
- **Timestamp queries:** optional `TIMESTAMP_QUERY` supports pass-boundary timestamps native/web; native-only `TIMESTAMP_QUERY_INSIDE_ENCODERS` / `INSIDE_PASSES` allow finer scopes. Resolve then copy to staging; multiply differences by `queue.get_timestamp_period()`. Request each required feature explicitly. [Official example](https://wgpu.rs/doc/wgpu_examples/timestamp_queries/index.html).
- **Storage formats:** portable write-storage options include r32{uint,sint,float}, rg32*, rgba8{unorm,snorm,uint,sint}, rgba16{uint,sint,float}, rgba32*; `bgra8unorm` requires its storage feature. No blanket storage support for sRGB, depth or compressed formats; query format capabilities. [WebGPU format table](https://gpuweb.github.io/gpuweb/#texture-format-caps).
- **Read/write textures:** browser spec supports read-only and read-write access, with read-write format restrictions (r32* baseline; newer tier features expand them). But wgpu 30 `StorageTextureAccess::{ReadOnly,ReadWrite}` documentation still requires native-only `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`. Treat this as a wrapper/spec mismatch to verify, and use ping-pong buffers or sampled-input/write-only-output textures for portability. [wgpu API](https://docs.rs/wgpu/30.0.1/wgpu/enum.StorageTextureAccess.html), [current spec](https://gpuweb.github.io/gpuweb/#texture-formats-tier2).
- **Other migration details:** 30 changes mapped writable views (use documented copy/write APIs rather than assuming `&mut [u8]`), and permits empty buffer slices but not empty bindings. 30.0.1 updates wasm-bindgen bindings to 0.2.127 and fixes null-adapter failure handling. Pin a coherent dependency set and follow versioned examples. [Release notes](https://github.com/gfx-rs/wgpu/releases).

## 4. amdgpu hangs and desktop responsiveness

Linux amdgpu defaults are **10,000 ms for non-compute jobs and 60,000 ms for compute jobs** on bare metal. `lockup_timeout` accepts one non-compute value or GFX,Compute,SDMA,Video values. These are scheduler-job watchdogs, not a portable per-dispatch allowance; Vulkan compute may execute on a graphics-capable queue, and browser watchdogs can intervene independently. [Kernel parameter/source documentation](https://kernel.googlesource.com/pub/scm/linux/kernel/git/robh/linux/+/707a63e9a9dd55432d47bf40457d4a3413888dcc/drivers/gpu/drm/amd/amdgpu/amdgpu_drv.c), [WebGPU device loss](https://gpuweb.github.io/gpuweb/#device-loss).

Recommendation, **not measured hardware thresholds**: begin with roughly 1–5 ms batches, keep only a small bounded number in flight, and adapt using GPU timestamps and observed UI latency. Split generations and spatial tiles into bounded dispatches/submissions; splitting dispatches while submitting an enormous uninterrupted backlog may still starve desktop work. Yield to the browser event loop between batches and handle device loss. Do not increase watchdog timeouts as a responsiveness strategy. These recommendations follow the scheduler timeout model and WebGPU's asynchronous [queue completion API](https://gpuweb.github.io/gpuweb/#dom-gpuqueue-onsubmittedworkdone).

CA correctness: use separate input/output states per generation and preserve generation-wide ordering; a workgroup barrier cannot synchronize all workgroups. Fusing many generations needs halo tiling or a different correct algorithm, not just a loop around an in-place global update. [WGSL synchronization scope](https://gpuweb.github.io/gpuweb/wgsl/#synchronization-builtin-functions).

## 5. Rust/WASM path and Linux browsers

- Use `wgpu = "30.0.1"`, `winit = "0.30"`, `wasm-bindgen`, `wasm-bindgen-futures`, and selected `web-sys` DOM/canvas features; wgpu defaults include `webgpu` and `wgsl`. Its WebGL backend is not a compute fallback. [wgpu features](https://docs.rs/crate/wgpu/30.0.1/features), [winit web](https://docs.rs/winit/0.30.13/winit/platform/web/index.html).
- Install `wasm32-unknown-unknown`; initialize asynchronously with `spawn_local`, use winit's web event-loop support and append/provide its canvas. Never block the browser main thread with native `pollster::block_on` or synchronous GPU waits. The official cross-platform [hello-triangle source](https://github.com/gfx-rs/wgpu/blob/v30.0.1/examples/features/src/hello_triangle/mod.rs) is the integration reference; compute-only apps do not require winit.
- Trunk route: an HTML entry containing `<link data-trunk rel="rust">`, then `trunk build --release`; Trunk runs wasm-bindgen and bundles assets. Use the maintained [repository guide](https://github.com/trunk-rs/trunk/tree/main/guide), not an arbitrary old tutorial domain.
- wasm-pack route: library `crate-type = ["cdylib", "rlib"]`, exported async initialization or `#[wasm_bindgen(start)]` that launches it; `wasm-pack build --target web --release`, then import/await generated JS initialization from the HTML module. Match wasm-bindgen CLI tooling to the resolved crate; serve over HTTPS or a trustworthy local origin. [wasm-pack build](https://rustwasm.github.io/docs/wasm-pack/commands/build.html), [wasm-bindgen examples](https://wasm-bindgen.github.io/wasm-bindgen/examples/without-a-bundler.html), [WebGPU secure context](https://gpuweb.github.io/gpuweb/#navigatorgpu).
- **Chrome/Linux AMD:** do not assume enabled by default. Chrome's troubleshooting guidance specifies `chrome://flags/#enable-unsafe-webgpu` and `#enable-vulkan` for experimental Linux support; enable graphics acceleration and inspect `chrome://gpu` for actual backend/blocklist status. `#ignore-gpu-blocklist` is a troubleshooting override when the GPU is blocked, not a universal requirement. [Google guidance](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips).
- **Firefox/Linux:** current Mozilla documentation still describes Linux as Nightly-enabled, with `dom.webgpu.enabled` as the controlling preference; stable support on Windows/Apple Silicon does not imply Linux release support. Prefer current Nightly for evaluation, inspect adapter availability and failures rather than promising the preference defeats every blocklist. [Mozilla status](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Experimental_features#webgpu_api).

Remaining evidence needed before an architecture decision: installed RADV/Vulkan limits, native wgpu exposed/requested limits, Chrome/Firefox adapter features and limits, then matched CA kernels with GPU timestamps and end-to-end timing. Public evidence supports neither a guaranteed 20% budget nor an inevitable order-of-magnitude loss on this GPU. [Limits contract](https://docs.rs/wgpu/30.0.1/wgpu/struct.Limits.html), [benchmark evidence](https://www.willusher.io/graphics/2024/04/22/webgpu-marching-cubes/).
